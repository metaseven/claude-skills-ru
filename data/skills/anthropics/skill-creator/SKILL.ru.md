# Skill Creator

Скил для создания новых скилов и их итеративного улучшения.

В общих чертах процесс создания скила выглядит так:

- Определи, что скил должен делать и примерно как
- Напиши черновик скила
- Придумай несколько тестовых промптов и запусти на них Claude с доступом к скилу
- Помоги пользователю оценить результаты как качественно, так и количественно
  - Пока запуски идут в фоне, набросай количественные эвалы, если их ещё нет (если они уже есть, можно использовать их как есть или изменить, если что-то нужно поправить). Затем объясни их пользователю (а если они уже существовали — объясни существующие)
  - Используй скрипт `eval-viewer/generate_review.py`, чтобы показать пользователю результаты для просмотра, а также дать ему взглянуть на количественные метрики
- Перепиши скил по обратной связи от пользователя, оценившего результаты (а также если в количественных бенчмарках проявятся явные недостатки)
- Повторяй, пока результат не устроит
- Расширь тестовый набор и повтори в большем масштабе

Твоя задача при работе с этим скилом — понять, на каком этапе этого процесса находится пользователь, и подключиться, помогая ему пройти дальнейшие стадии. Например, пользователь может сказать: «Я хочу сделать скил для X». Ты можешь помочь уточнить, что он имеет в виду, написать черновик, написать тестовые случаи, определить, как он хочет проводить оценку, запустить все промпты и повторить цикл.

С другой стороны, у пользователя может уже быть черновик скила. Тогда можно сразу переходить к части с эвалами и итерациями.

Конечно, всегда оставайся гибким: если пользователь говорит «мне не нужно гонять кучу эвалов, давай просто поработаем по ощущениям», так и делай.

А когда скил готов (хотя порядок, опять же, гибкий), можно также запустить оптимизатор описания скила — для него есть отдельный скрипт — чтобы улучшить срабатывание скила.

Договорились? Отлично.

## Общение с пользователем

Skill creator, вероятно, будут использовать люди с самым разным уровнем знакомства с программистским жаргоном. Если ты не в курсе (а откуда бы — это началось совсем недавно), сейчас есть тренд: возможности Claude вдохновляют сантехников открывать терминалы, а родителей и бабушек с дедушками — гуглить «как установить npm». С другой стороны, основная масса пользователей, скорее всего, вполне уверенно обращается с компьютером.

Поэтому внимательно следи за контекстными подсказками, чтобы понять, как формулировать свои сообщения! По умолчанию, просто чтобы ты представлял себе ориентиры:

- «эвалы» и «бенчмарк» — пограничные термины, но допустимые
- для «JSON» и «assertion» (проверочное утверждение) нужны серьёзные признаки того, что пользователь знает, что это такое, прежде чем использовать их без объяснения

Если сомневаешься, кратко поясни термин; не стесняйся дать короткое определение, если не уверен, что пользователь поймёт.

## Создание скила

### Выяснение замысла

Начни с понимания замысла пользователя. В текущем разговоре уже может содержаться процесс, который пользователь хочет зафиксировать (например, он говорит «преврати это в скил»). Если так, сначала извлеки ответы из истории разговора: использованные инструменты, последовательность шагов, исправления пользователя, наблюдаемые форматы входных и выходных данных. Пробелы может восполнить пользователь, и перед переходом к следующему шагу он должен подтвердить результат.

1. Что этот скил должен позволять Claude делать?
2. Когда скил должен срабатывать? (какие фразы и контексты пользователя)
3. Каков ожидаемый формат результата?
4. Нужно ли настраивать тестовые случаи, чтобы проверить, что скил работает? Скилам с объективно проверяемым результатом (преобразование файлов, извлечение данных, генерация кода, фиксированные шаги процесса) тестовые случаи полезны. Скилам с субъективным результатом (стиль письма, искусство) они часто не нужны. Предложи подходящий вариант по умолчанию в зависимости от типа скила, но решение оставь пользователю.

### Интервью и исследование

Проактивно задавай вопросы о граничных случаях, форматах входных и выходных данных, примерах файлов, критериях успеха и зависимостях. Не пиши тестовые промпты, пока эта часть не будет проработана.

Проверь доступные MCP: если они полезны для исследования (поиск по документации, поиск похожих скилов, изучение лучших практик), веди исследование параллельно через субагентов, если они доступны, иначе — самостоятельно. Приходи с подготовленным контекстом, чтобы снизить нагрузку на пользователя.

### Написание SKILL.md

На основе интервью с пользователем заполни следующие компоненты:

- **name**: идентификатор скила
- **description**: когда срабатывать и что делает скил. Это основной механизм срабатывания — включи и то, что скил делает, И конкретные контексты, когда его использовать. Вся информация о том, когда применять скил, должна быть здесь, а не в теле. Примечание: сейчас у Claude есть склонность «недосрабатывать» со скилами — не использовать их, когда они были бы полезны. Чтобы с этим бороться, делай описания скилов немного «напористыми». Например, вместо «Как собрать простой быстрый дашборд для отображения внутренних данных Anthropic.» можно написать «Как собрать простой быстрый дашборд для отображения внутренних данных Anthropic. Обязательно используй этот скил, когда пользователь упоминает дашборды, визуализацию данных, внутренние метрики или хочет отобразить любые данные компании, даже если он прямо не просит «дашборд»».
- **compatibility**: необходимые инструменты и зависимости (необязательно, нужно редко)
- **всё остальное в скиле :)**

### Руководство по написанию скилов

#### Анатомия скила

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### Постепенное раскрытие

Скилы используют трёхуровневую систему загрузки:
1. **Метаданные** (name + description) — всегда в контексте (~100 слов)
2. **Тело SKILL.md** — в контексте всякий раз, когда скил срабатывает (идеально <500 строк)
3. **Вложенные ресурсы** — по мере необходимости (без ограничений, скрипты могут выполняться без загрузки в контекст)

Эти количества слов приблизительные; при необходимости можно выходить за них.

**Ключевые приёмы:**
- Держи SKILL.md короче 500 строк; если приближаешься к этому пределу, добавь ещё один уровень иерархии и чёткие указатели, куда модели, использующей скил, идти дальше.
- Явно ссылайся на вложенные файлы из SKILL.md и поясняй, когда их читать
- Для больших справочных файлов (>300 строк) добавляй оглавление

**Организация по областям**: если скил поддерживает несколько областей или фреймворков, организуй материал по вариантам:
```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude читает только нужный справочный файл.

#### Принцип отсутствия неожиданностей

Это само собой разумеется, но скилы не должны содержать вредоносный код, эксплойты или любой контент, который может нарушить безопасность системы. Содержимое скила не должно удивлять пользователя, если описать его назначение. Не поддерживай просьбы создать вводящие в заблуждение скилы или скилы, призванные облегчить несанкционированный доступ, утечку данных или иную вредоносную деятельность. А вот что-то вроде «сыграй роль XYZ» — допустимо.

#### Шаблоны написания

Предпочитай повелительное наклонение в инструкциях.

**Определение форматов вывода** — можно сделать так:
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**Шаблон примеров** — полезно включать примеры. Их можно оформить так (но если в примерах есть «Input» и «Output», можно немного отойти от этого формата):
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

### Стиль написания

Старайся объяснять модели, почему что-то важно, вместо тяжеловесных замшелых MUST. Используй теорию разума и делай скил общим, а не узко заточенным под конкретные примеры. Начни с черновика, затем посмотри на него свежим взглядом и улучши.

### Тестовые случаи

После написания черновика скила придумай 2–3 реалистичных тестовых промпта — таких, какие реальный пользователь действительно мог бы написать. Покажи их пользователю: [необязательно использовать именно эту формулировку] «Вот несколько тестовых случаев, которые я хотел бы попробовать. Они подходят или хочешь добавить ещё?» Затем запусти их.

Сохрани тестовые случаи в `evals/evals.json`. Пока не пиши проверочные утверждения — только промпты. Утверждения ты набросаешь на следующем шаге, пока идут запуски.

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

Полную схему (включая поле `assertions`, которое ты добавишь позже) см. в `references/schemas.md`.

## Запуск и оценка тестовых случаев

Этот раздел — одна непрерывная последовательность, не останавливайся на полпути. НИКОГДА не используй `/skill-test` или любой другой скил для тестирования.

Складывай результаты в `<skill-name>-workspace/` рядом с директорией скила (на одном уровне с ней). Внутри рабочей директории организуй результаты по итерациям (`iteration-1/`, `iteration-2/` и т. д.), а внутри итерации у каждого тестового случая своя директория (`eval-0/`, `eval-1/` и т. д.). Не создавай всё это заранее — создавай директории по ходу работы.

### Шаг 1: Запусти все прогоны (со скилом И базовые) в одном ходе

Для каждого тестового случая запусти двух субагентов в одном ходе: одного со скилом, другого без. Это важно: не запускай сначала прогоны со скилом, а потом возвращайся за базовыми. Запускай всё сразу, чтобы всё завершилось примерно одновременно.

**Прогон со скилом:**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**Базовый прогон** (тот же промпт, но базовый вариант зависит от контекста):
- **Создание нового скила**: вообще без скила. Тот же промпт, без пути к скилу, результат сохраняется в `without_skill/outputs/`.
- **Улучшение существующего скила**: старая версия. Перед редактированием сделай снимок скила (`cp -r <skill-path> <workspace>/skill-snapshot/`), затем направь базового субагента на этот снимок. Сохраняй результат в `old_skill/outputs/`.

Напиши `eval_metadata.json` для каждого тестового случая (утверждения пока могут быть пустыми). Дай каждому эвалу описательное имя в соответствии с тем, что он проверяет, а не просто «eval-0». Используй это имя и для директории. Если в этой итерации используются новые или изменённые промпты эвалов, создай эти файлы для каждой новой директории эвала — не рассчитывай, что они сохранятся с предыдущих итераций.

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### Шаг 2: Пока идут прогоны, набросай проверочные утверждения

Не просто жди завершения прогонов — используй это время с пользой. Набросай количественные проверочные утверждения для каждого тестового случая и объясни их пользователю. Если утверждения уже есть в `evals/evals.json`, просмотри их и объясни, что они проверяют.

Хорошие утверждения объективно проверяемы и имеют описательные названия: они должны ясно читаться в просмотрщике бенчмарка, чтобы любой, кто бегло взглянет на результаты, сразу понимал, что проверяет каждое из них. Субъективные скилы (стиль письма, качество дизайна) лучше оценивать качественно — не навязывай утверждения тому, что требует человеческого суждения.

Когда утверждения готовы, обнови файлы `eval_metadata.json` и `evals/evals.json`. Также объясни пользователю, что он увидит в просмотрщике — как качественные результаты, так и количественный бенчмарк.

### Шаг 3: По мере завершения прогонов фиксируй данные о времени

Когда каждая задача субагента завершается, ты получаешь уведомление с `total_tokens` и `duration_ms`. Немедленно сохрани эти данные в `timing.json` в директории прогона:

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

Это единственная возможность зафиксировать эти данные — они приходят через уведомление задачи и больше нигде не сохраняются. Обрабатывай каждое уведомление по мере поступления, а не пытайся накапливать их пачкой.

### Шаг 4: Оцени, агрегируй и запусти просмотрщик

Когда все прогоны завершены:

1. **Оцени каждый прогон** — запусти субагента-оценщика (или оцени самостоятельно), который прочитает `agents/grader.md` и проверит каждое утверждение по результатам. Сохрани итоги в `grading.json` в директории каждого прогона. Массив expectations в grading.json ДОЛЖЕН использовать поля `text`, `passed` и `evidence` (а не `name`/`met`/`details` или другие варианты) — просмотрщик зависит именно от этих названий полей. Утверждения, которые можно проверить программно, проверяй написанным и запущенным скриптом, а не на глаз — скрипты быстрее, надёжнее и могут использоваться повторно в последующих итерациях.

2. **Агрегируй в бенчмарк** — запусти скрипт агрегации из директории skill-creator:
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   Он создаёт `benchmark.json` и `benchmark.md` с pass_rate, временем и токенами для каждой конфигурации, со средним ± стандартное отклонение и дельтой. Если генерируешь benchmark.json вручную, точную схему, которую ожидает просмотрщик, см. в `references/schemas.md`.
Размещай каждую версию со скилом перед соответствующей базовой версией.

3. **Проведи аналитический проход** — прочитай данные бенчмарка и выяви закономерности, которые агрегированная статистика может скрывать. Что искать, см. в `agents/analyzer.md` (раздел «Analyzing Benchmark Results»): например, утверждения, которые всегда проходят независимо от скила (недискриминирующие), эвалы с большим разбросом (возможно, нестабильные) и компромиссы между временем и токенами.

4. **Запусти просмотрщик** с качественными результатами и количественными данными:
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   Для итерации 2 и далее дополнительно передай `--previous-workspace <workspace>/iteration-<N-1>`.

   **Cowork / среды без интерфейса:** если `webbrowser.open()` недоступен или у среды нет дисплея, используй `--static <output_path>`, чтобы записать автономный HTML-файл вместо запуска сервера. Обратная связь будет скачана как файл `feedback.json`, когда пользователь нажмёт «Submit All Reviews». После скачивания скопируй `feedback.json` в рабочую директорию, чтобы следующая итерация его подхватила.

Примечание: используй generate_review.py для создания просмотрщика; писать собственный HTML не нужно.

5. **Сообщи пользователю** что-то вроде: «Я открыл результаты в твоём браузере. Там две вкладки: "Outputs" позволяет пройтись по каждому тестовому случаю и оставить обратную связь, "Benchmark" показывает количественное сравнение. Когда закончишь, вернись сюда и дай мне знать».

### Что пользователь видит в просмотрщике

Вкладка «Outputs» показывает по одному тестовому случаю:
- **Prompt**: поставленная задача
- **Output**: файлы, созданные скилом, по возможности отображаются прямо на странице
- **Previous Output** (итерация 2+): свёрнутый раздел с результатом предыдущей итерации
- **Formal Grades** (если запускалась оценка): свёрнутый раздел с прохождением и провалом утверждений
- **Feedback**: текстовое поле с автосохранением по мере ввода
- **Previous Feedback** (итерация 2+): комментарии с прошлого раза, показаны под текстовым полем

Вкладка «Benchmark» показывает сводную статистику: pass rate, время и использование токенов для каждой конфигурации, с разбивкой по эвалам и наблюдениями аналитика.

Навигация — кнопками «назад/вперёд» или стрелками на клавиатуре. Закончив, пользователь нажимает «Submit All Reviews», и вся обратная связь сохраняется в `feedback.json`.

### Шаг 5: Прочитай обратную связь

Когда пользователь сообщает, что закончил, прочитай `feedback.json`:

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

Пустая обратная связь означает, что пользователя всё устроило. Сосредоточь улучшения на тех тестовых случаях, к которым у пользователя были конкретные замечания.

Когда закончишь работу с просмотрщиком, останови его сервер:

```bash
kill $VIEWER_PID 2>/dev/null
```

## Улучшение скила

Это ядро всего цикла. Ты прогнал тестовые случаи, пользователь просмотрел результаты, и теперь нужно улучшить скил на основе его обратной связи.

### Как думать об улучшениях

1. **Обобщай обратную связь.** Главное, что здесь происходит: мы пытаемся создавать скилы, которые можно использовать миллион раз (может быть, буквально, а может, и больше — кто знает) на множестве разных промптов. Вы с пользователем итерируетесь лишь на нескольких примерах снова и снова, потому что так быстрее. Пользователь знает эти примеры вдоль и поперёк, и ему легко оценивать новые результаты. Но если скил, который вы разрабатываете вместе, работает только на этих примерах, он бесполезен. Вместо дотошных, переобученных под примеры правок или гнетуще ограничивающих ОБЯЗАТЕЛЬНО, при упорной проблеме можно попробовать пойти вширь: использовать другие метафоры или порекомендовать другие паттерны работы. Попробовать относительно дёшево, и, возможно, ты найдёшь что-то отличное.

2. **Держи промпт компактным.** Убирай то, что не приносит пользы. Обязательно читай транскрипты, а не только итоговые результаты: если видно, что скил заставляет модель тратить много времени на непродуктивные действия, попробуй убрать те части скила, которые к этому приводят, и посмотри, что получится.

3. **Объясняй, почему.** Старайся изо всех сил объяснять, **почему** ты просишь модель делать то или иное. Современные LLM *умные*. У них хорошая теория разума, и при хорошей обвязке они способны выходить за рамки механических инструкций и по-настоящему добиваться результата. Даже если обратная связь от пользователя лаконична или раздражённа, постарайся действительно понять задачу, понять, почему пользователь написал то, что написал, и что именно он написал, а затем передай это понимание в инструкциях. Если ловишь себя на том, что пишешь ВСЕГДА или НИКОГДА капсом или используешь сверхжёсткие структуры, это жёлтый флаг: по возможности переформулируй и объясни логику, чтобы модель понимала, почему просимое важно. Это более человечный, мощный и эффективный подход.

4. **Ищи повторяющуюся работу в тестовых случаях.** Читай транскрипты тестовых прогонов и замечай, не писали ли субагенты независимо друг от друга похожие вспомогательные скрипты и не применяли ли один и тот же многошаговый подход к чему-либо. Если во всех 3 тестовых случаях субагент написал `create_docx.py` или `build_chart.py`, это сильный сигнал, что скил должен включать этот скрипт. Напиши его один раз, положи в `scripts/` и скажи скилу его использовать. Это избавит каждый будущий вызов от изобретения велосипеда.

Эта задача довольно важна (мы пытаемся создать миллиарды экономической ценности в год!), а твоё время на размышления — не узкое место, так что не торопись и как следует всё обдумай. Советую написать черновик правок, затем взглянуть на него заново и улучшить. Постарайся по-настоящему влезть в голову пользователя и понять, что ему нужно и чего он хочет.

### Цикл итераций

После улучшения скила:

1. Примени свои улучшения к скилу
2. Перезапусти все тестовые случаи в новую директорию `iteration-<N+1>/`, включая базовые прогоны. Если создаёшь новый скил, базовый вариант всегда `without_skill` (без скила) — он остаётся одним и тем же во всех итерациях. Если улучшаешь существующий скил, действуй по своему усмотрению: базовым может быть исходная версия, с которой пришёл пользователь, или предыдущая итерация.
3. Запусти просмотрщик с `--previous-workspace`, указывающим на предыдущую итерацию
4. Дождись, пока пользователь просмотрит результаты и скажет, что закончил
5. Прочитай новую обратную связь, улучши снова, повтори

Продолжай, пока:
- пользователь не скажет, что доволен
- вся обратная связь не окажется пустой (всё выглядит хорошо)
- ты не перестанешь добиваться значимого прогресса

## Дополнительно: слепое сравнение

Для ситуаций, когда нужно более строгое сравнение двух версий скила (например, пользователь спрашивает: «новая версия действительно лучше?»), есть система слепого сравнения. Подробности см. в `agents/comparator.md` и `agents/analyzer.md`. Основная идея: дай два результата независимому агенту, не говоря, какой из них какой, и пусть он оценит качество. Затем проанализируй, почему победитель победил.

Это необязательно, требует субагентов, и большинству пользователей не понадобится. Обычно достаточно цикла с человеческой оценкой.

## Оптимизация описания

Поле description во frontmatter SKILL.md — основной механизм, определяющий, вызовет ли Claude скил. После создания или улучшения скила предложи оптимизировать описание для более точного срабатывания.

### Шаг 1: Сгенерируй запросы для эвалов срабатывания

Создай 20 запросов для эвалов — смесь тех, где скил должен срабатывать, и тех, где не должен. Сохрани как JSON:

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

Запросы должны быть реалистичными, такими, какие действительно напечатал бы пользователь Claude Code или Claude.ai. Не абстрактные просьбы, а конкретные и подробные запросы. Например, с путями к файлам, личным контекстом о работе или ситуации пользователя, названиями столбцов и значениями, названиями компаний, URL. С небольшой предысторией. Некоторые могут быть в нижнем регистре, содержать сокращения, опечатки или разговорные выражения. Используй смесь разной длины и сосредоточься на пограничных случаях, а не на однозначных (пользователь получит возможность их утвердить).

Плохо: `"Format this data"`, `"Extract text from PDF"`, `"Create a chart"`

Хорошо: `"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

Для запросов, где скил **должен сработать** (8–10), продумай охват. Нужны разные формулировки одного и того же намерения — и формальные, и разговорные. Включи случаи, когда пользователь прямо не называет скил или тип файла, но явно в нём нуждается. Добавь необычные сценарии использования и случаи, когда этот скил конкурирует с другим, но должен победить.

Для запросов, где скил **не должен срабатывать** (8–10), самые ценные — «почти попадания»: запросы, у которых общие ключевые слова или понятия со скилом, но на самом деле нужно что-то другое. Подумай о смежных областях, неоднозначных формулировках, когда наивное совпадение по ключевым словам сработало бы, но не должно, и о случаях, когда запрос затрагивает то, что скил умеет, но в контексте, где уместнее другой инструмент.

Главное, чего следует избегать: не делай запросы, где скил не должен срабатывать, очевидно нерелевантными. «Напиши функцию Фибоначчи» в роли отрицательного теста для PDF-скила слишком просто, он ничего не проверяет. Отрицательные случаи должны быть по-настоящему каверзными.

### Шаг 2: Проверь с пользователем

Покажи пользователю набор эвалов на проверку, используя HTML-шаблон:

1. Прочитай шаблон из `assets/eval_review.html`
2. Замени плейсхолдеры:
   - `__EVAL_DATA_PLACEHOLDER__` → JSON-массив элементов эвала (без кавычек вокруг — это присваивание JS-переменной)
   - `__SKILL_NAME_PLACEHOLDER__` → имя скила
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → текущее описание скила
3. Запиши во временный файл (например, `/tmp/eval_review_<skill-name>.html`) и открой его: `open /tmp/eval_review_<skill-name>.html`
4. Пользователь может редактировать запросы, переключать should-trigger, добавлять и удалять записи, а затем нажать «Export Eval Set»
5. Файл скачивается в `~/Downloads/eval_set.json` — проверь папку Downloads на предмет самой свежей версии на случай, если файлов несколько (например, `eval_set (1).json`)

Этот шаг важен: плохие запросы для эвалов приводят к плохим описаниям.

### Шаг 3: Запусти цикл оптимизации

Скажи пользователю: «Это займёт некоторое время — я запущу цикл оптимизации в фоне и буду периодически проверять его».

Сохрани набор эвалов в рабочую директорию, затем запусти в фоне:

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

Используй ID модели из своего системного промпта (той, что обеспечивает текущую сессию), чтобы проверка срабатывания соответствовала тому, что пользователь реально увидит.

Пока скрипт работает, периодически смотри конец вывода (tail), чтобы информировать пользователя, на какой итерации он находится и каковы результаты.

Скрипт автоматически проходит весь цикл оптимизации. Он делит набор эвалов на 60% обучающих и 40% отложенных тестовых, оценивает текущее описание (запуская каждый запрос 3 раза для надёжной оценки доли срабатываний), затем обращается к Claude, чтобы тот предложил улучшения на основе неудач. Он заново оценивает каждое новое описание на обучающей и тестовой выборках, повторяя до 5 раз. По завершении он открывает в браузере HTML-отчёт с результатами по каждой итерации и возвращает JSON с `best_description` — оно выбирается по результату на тесте, а не на обучении, чтобы избежать переобучения.

### Как работает срабатывание скилов

Понимание механизма срабатывания помогает составлять более удачные запросы для эвалов. Скилы появляются в списке `available_skills` у Claude со своим именем и описанием, и Claude решает, обращаться ли к скилу, на основе этого описания. Важно знать: Claude обращается к скилам только для задач, с которыми не может легко справиться сам — простые одношаговые запросы вроде «прочитай этот PDF» могут не вызвать скил, даже если описание идеально подходит, потому что Claude справляется с ними напрямую базовыми инструментами. Сложные, многошаговые или специализированные запросы надёжно вызывают скилы, если описание подходит.

Это значит, что запросы для твоих эвалов должны быть достаточно содержательными, чтобы Claude действительно выиграл от обращения к скилу. Простые запросы вроде «прочитай файл X» — плохие тестовые случаи: они не вызовут скилы независимо от качества описания.

### Шаг 4: Примени результат

Возьми `best_description` из JSON-вывода и обнови frontmatter SKILL.md скила. Покажи пользователю описание до и после и сообщи результаты.

Проверь, есть ли у тебя доступ к инструменту `present_files`. Если нет, пропусти этот шаг. Если есть, упакуй скил и передай пользователю файл .skill:

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

После упаковки направь пользователя к полученному пути файла `.skill`, чтобы он мог его установить.

## Инструкции для Claude.ai

В Claude.ai основной процесс тот же (черновик → тест → ревью → улучшение → повтор), но поскольку в Claude.ai нет субагентов, некоторые механики меняются. Вот к чему нужно адаптироваться:

**Запуск тестовых случаев**: нет субагентов — значит, нет параллельного выполнения. Для каждого тестового случая прочитай SKILL.md скила, затем следуй его инструкциям и выполни тестовый промпт самостоятельно. Делай их по одному. Это менее строго, чем независимые субагенты (ты сам написал скил и сам же его запускаешь, поэтому у тебя полный контекст), но это полезная проверка здравого смысла, а человеческое ревью компенсирует недостаток. Пропусти базовые прогоны — просто используй скил, чтобы выполнить задачу как запрошено.

**Просмотр результатов**: если не можешь открыть браузер (например, у виртуальной машины Claude.ai нет дисплея или ты работаешь на удалённом сервере), полностью пропусти браузерный просмотрщик. Вместо этого показывай результаты прямо в разговоре. Для каждого тестового случая покажи промпт и результат. Если результат — файл, который пользователю нужно увидеть (например, .docx или .xlsx), сохрани его в файловой системе и скажи, где он лежит, чтобы пользователь мог скачать и проверить. Запроси обратную связь прямо в чате: «Как тебе? Что-нибудь изменил бы?»

**Бенчмаркинг**: пропусти количественный бенчмаркинг — он опирается на сравнение с базовыми прогонами, которое без субагентов лишено смысла. Сосредоточься на качественной обратной связи от пользователя.

**Цикл итераций**: тот же, что и раньше: улучши скил, перезапусти тестовые случаи, запроси обратную связь — только без браузерного просмотрщика посередине. Если есть файловая система, результаты по-прежнему можно организовывать в директории итераций.

**Оптимизация описания**: этому разделу требуется инструмент CLI `claude` (а именно `claude -p`), который доступен только в Claude Code. Если ты в Claude.ai, пропусти его.

**Слепое сравнение**: требует субагентов. Пропусти.

**Упаковка**: скрипт `package_skill.py` работает везде, где есть Python и файловая система. В Claude.ai можно запустить его, и пользователь сможет скачать полученный файл `.skill`.

**Обновление существующего скила**: пользователь может просить обновить существующий скил, а не создать новый. В этом случае:
- **Сохрани исходное имя.** Запомни имя директории скила и поле `name` во frontmatter и используй их без изменений. Например, если установленный скил называется `research-helper`, результатом должен быть `research-helper.skill` (а не `research-helper-v2`).
- **Скопируй в доступное для записи место перед редактированием.** Путь установленного скила может быть только для чтения. Скопируй в `/tmp/skill-name/`, редактируй там и упаковывай из копии.
- **Если пакуешь вручную, сначала подготовь всё в `/tmp/`**, а затем скопируй в выходную директорию — прямая запись может не пройти из-за прав доступа.

## Инструкции для Cowork

Если ты работаешь в Cowork, главное, что нужно знать:

- У тебя есть субагенты, так что основной процесс (параллельный запуск тестовых случаев, базовые прогоны, оценка и т. д.) работает целиком. (Однако при серьёзных проблемах с таймаутами можно запускать тестовые промпты последовательно, а не параллельно.)
- У тебя нет браузера и дисплея, поэтому при генерации просмотрщика эвалов используй `--static <output_path>`, чтобы записать автономный HTML-файл вместо запуска сервера. Затем предложи ссылку, по которой пользователь сможет открыть HTML в своём браузере.
- По какой-то причине настройка Cowork, похоже, отбивает у Claude желание генерировать просмотрщик эвалов после запуска тестов, поэтому, чтобы повторить: независимо от того, в Cowork ты или в Claude Code, после запуска тестов ты ВСЕГДА должен сгенерировать просмотрщик эвалов, чтобы человек посмотрел на примеры, прежде чем самостоятельно переделывать скил и пытаться вносить правки, — используя `generate_review.py` (а не собственный самодельный HTML-код). Заранее прошу прощения, но тут я перейду на капс: СГЕНЕРИРУЙ ПРОСМОТРЩИК ЭВАЛОВ *ДО* ТОГО, КАК САМОСТОЯТЕЛЬНО ОЦЕНИВАТЬ ВХОДНЫЕ ДАННЫЕ. Нужно как можно скорее показать их человеку!
- Обратная связь работает иначе: поскольку сервер не запущен, кнопка «Submit All Reviews» в просмотрщике скачает `feedback.json` как файл. Затем ты сможешь прочитать его оттуда (возможно, придётся сначала запросить доступ).
- Упаковка работает — `package_skill.py` нужны только Python и файловая система.
- Оптимизация описания (`run_loop.py` / `run_eval.py`) должна нормально работать в Cowork, поскольку использует `claude -p` через subprocess, а не браузер, но отложи её до тех пор, пока полностью не закончишь делать скил и пользователь не согласится, что он в хорошем состоянии.

## Справочные файлы

В директории agents/ лежат инструкции для специализированных субагентов. Читай их, когда нужно запустить соответствующего субагента.

- `agents/grader.md` — как оценивать утверждения по результатам
- `agents/comparator.md` — как проводить слепое A/B-сравнение двух результатов
- `agents/analyzer.md` — как анализировать, почему одна версия победила другую

В директории references/ лежит дополнительная документация:
- `references/schemas.md` — структуры JSON для evals.json, grading.json и т. д.
