# Написание скилов

## Обзор

**Написание скилов — это Test-Driven Development, применённый к документации процессов.**

**Персональные скилы лежат в каталоге скилов вашей среды выполнения** (`~/.claude/skills/` в Claude Code) — путь для других сред смотри в [codex-tools.md](../using-superpowers/references/codex-tools.md) или [gemini-tools.md](../using-superpowers/references/gemini-tools.md). Codex, Copilot CLI и Gemini CLI также распознают `~/.agents/skills/` как кросс-средовой алиас.

Ты пишешь тест-кейсы (сценарии давления для субагентов), наблюдаешь, как они падают (базовое поведение), пишешь скил (документацию), наблюдаешь, как тесты проходят (агенты следуют скилу), и проводишь рефакторинг (закрываешь лазейки).

**Ключевой принцип:** если ты не видел, как агент ошибается без скила, ты не знаешь, учит ли скил правильным вещам.

**ОБЯЗАТЕЛЬНАЯ БАЗА:** ты ОБЯЗАН понимать superpowers:test-driven-development, прежде чем использовать этот скил. Тот скил определяет базовый цикл RED-GREEN-REFACTOR. Этот скил адаптирует TDD для документации.

**Официальные рекомендации:** официальные рекомендации Anthropic по написанию скилов смотри в references/anthropic-best-practices.md. Этот документ даёт дополнительные паттерны и правила, дополняющие подход на основе TDD из этого скила.

## Что такое скил?

**Скил** — это справочное руководство по проверенным техникам, паттернам или инструментам. Скилы помогают будущим агентам находить и применять эффективные подходы.

**Скилы — это:** переиспользуемые техники, паттерны, инструменты, справочные руководства

**Скилы — это НЕ:** рассказы о том, как ты однажды решил проблему

## Соответствие TDD и скилов

| Понятие TDD | Создание скила |
|-------------|----------------|
| **Тест-кейс** | Сценарий давления для субагента |
| **Production-код** | Документ скила (SKILL.md) |
| **Тест падает (RED)** | Агент нарушает правило без скила (базовый прогон) |
| **Тест проходит (GREEN)** | Агент следует скилу, когда он доступен |
| **Рефакторинг** | Закрыть лазейки, сохранив соблюдение правил |
| **Сначала написать тест** | Запустить базовый сценарий ДО написания скила |
| **Увидеть падение** | Задокументировать точные оправдания агента |
| **Минимум кода** | Написать скил, закрывающий именно эти нарушения |
| **Увидеть прохождение** | Убедиться, что агент теперь следует правилу |
| **Цикл рефакторинга** | Найти новые оправдания → закрыть → перепроверить |

Весь процесс создания скила следует циклу RED-GREEN-REFACTOR.

## Когда создавать скил

**Создавай, когда:**
- Техника не была интуитивно очевидной для тебя
- Ты будешь обращаться к ней снова в разных проектах
- Паттерн применим широко (не привязан к проекту)
- Он будет полезен другим

**Не создавай для:**
- Разовых решений
- Стандартных практик, хорошо описанных в других местах
- Конвенций конкретного проекта (помести их в файл с инструкциями)
- Механических ограничений (если их можно проверить регулярным выражением или валидацией — автоматизируй, а документацию оставь для решений, требующих суждения)

## Типы скилов

### Техника
Конкретный метод с шагами (condition-based-waiting, root-cause-tracing)

### Паттерн
Способ мышления о проблемах (flatten-with-flags, test-invariants)

### Справочник
Документация API, руководства по синтаксису, документация инструментов (office docs)

## Структура каталогов


```
skills/
  skill-name/
    SKILL.md              # Main reference (required)
    supporting-file.*     # Only if needed
```

**Плоское пространство имён** — все скилы в одном доступном для поиска пространстве

**Отдельные файлы для:**
1. **Объёмных справочников** (100+ строк) — документация API, подробный синтаксис
2. **Переиспользуемых инструментов** — скрипты, утилиты, шаблоны

**Оставляй внутри файла:**
- Принципы и концепции
- Паттерны кода (< 50 строк)
- Всё остальное

## Написание SKILL.md

`description` скила говорит только о том, когда его использовать: условия
срабатывания и симптомы, начиная с «Используй при...» (в оригинале — «Use when...»). Он никогда не пересказывает
процесс скила, потому что агент, прочитавший краткое изложение процесса, будет
следовать ему вместо того, чтобы читать сам скил.

Когда ты пишешь или меняешь frontmatter, имя или описание скила, либо
тебе нужно сократить его размер, прочитай [references/discovery.md](references/discovery.md):
шаблон SKILL.md, рекомендации по описанию и ключевым словам, именованию, бюджетам токенов
и перекрёстным ссылкам на другие скилы.

## Примеры кода

**Один отличный пример лучше многих посредственных**

Выбирай наиболее подходящий язык:
- Техники тестирования → TypeScript/JavaScript
- Отладка систем → Shell/Python
- Обработка данных → Python

**Хороший пример:**
- Полный и запускаемый
- Хорошо прокомментирован, объясняет ПОЧЕМУ
- Взят из реального сценария
- Чётко показывает паттерн
- Готов к адаптации (не обобщённый шаблон)

**Не делай:**
- Реализации на 5+ языках
- Шаблоны «заполни пропуски»
- Надуманные примеры

Ты хорошо умеешь портировать — одного отличного примера достаточно.

## Организация файлов

### Самодостаточный скил
```
defense-in-depth/
  SKILL.md    # Everything inline
```
Когда: всё содержимое помещается, объёмный справочник не нужен

### Скил с переиспользуемым инструментом
```
condition-based-waiting/
  SKILL.md    # Overview + patterns
  example.ts  # Working helpers to adapt
```
Когда: инструмент — это переиспользуемый код, а не просто текст

### Скил с объёмным справочником
```
pptx/
  SKILL.md       # Overview + workflows
  pptxgenjs.md   # 600 lines API reference
  ooxml.md       # 500 lines XML structure
  scripts/       # Executable tools
```
Когда: справочный материал слишком велик, чтобы держать его внутри файла

Вызывай прилагаемые скрипты через интерпретатор прямо в тексте (`bash scripts/tool.sh`, `node scripts/tool.js`), никогда не по голому пути: некоторые упаковщики плагинов для сред выполнения убирают биты исполнения, и голый `scripts/tool.sh` там падает с `Permission denied`.

## Железный закон (такой же, как в TDD)

```
NO SKILL WITHOUT A FAILING TEST FIRST
```

Это относится к НОВЫМ скилам И к ПРАВКАМ существующих скилов.

Написал скил до тестирования? Удали его. Начни заново.
Отредактировал скил без тестирования? Это то же нарушение.

**Никаких исключений:**
- Ни для «простых дополнений»
- Ни для «просто добавил раздел»
- Ни для «обновлений документации»
- Не храни непротестированные изменения «для справки»
- Не «подгоняй» во время прогона тестов
- Удалить значит удалить

**ОБЯЗАТЕЛЬНАЯ БАЗА:** скил superpowers:test-driven-development объясняет, почему это важно. Те же принципы применимы к документации.

## Тестирование скилов всех типов

Разным типам скилов нужны разные подходы к тестированию:

### Скилы, обеспечивающие дисциплину (правила/требования)

**Примеры:** TDD, verification-before-completion, designing-before-coding

**Тестируй с помощью:**
- Академических вопросов: понимают ли они правила?
- Сценариев давления: следуют ли они правилам под стрессом?
- Нескольких давлений одновременно: время + вложенные усилия + усталость
- Выявляй оправдания и добавляй явные контраргументы

**Критерий успеха:** агент следует правилу при максимальном давлении

### Скилы-техники (практические руководства)

**Примеры:** condition-based-waiting, root-cause-tracing, defensive-programming

**Тестируй с помощью:**
- Сценариев применения: могут ли они правильно применить технику?
- Сценариев с вариациями: справляются ли они с пограничными случаями?
- Тестов на недостающую информацию: есть ли в инструкциях пробелы?

**Критерий успеха:** агент успешно применяет технику в новом сценарии

### Скилы-паттерны (ментальные модели)

**Примеры:** reducing-complexity, концепции information-hiding

**Тестируй с помощью:**
- Сценариев распознавания: распознают ли они, когда применим паттерн?
- Сценариев применения: могут ли они использовать ментальную модель?
- Контрпримеров: знают ли они, когда НЕ применять?

**Критерий успеха:** агент правильно определяет, когда и как применять паттерн

### Скилы-справочники (документация/API)

**Примеры:** документация API, справочники команд, руководства по библиотекам

**Тестируй с помощью:**
- Сценариев поиска: могут ли они найти нужную информацию?
- Сценариев применения: могут ли они правильно использовать найденное?
- Проверки на пробелы: охвачены ли типичные сценарии использования?

**Критерий успеха:** агент находит и правильно применяет справочную информацию

## Типичные оправдания для пропуска тестирования

| Отговорка | Реальность |
|-----------|------------|
| «Скил и так очевидно понятен» | Понятно тебе ≠ понятно другим агентам. Протестируй. |
| «Это всего лишь справочник» | В справочниках бывают пробелы и неясные места. Протестируй поиск. |
| «Тестирование — это перебор» | В непротестированных скилах есть проблемы. Всегда. 15 минут тестирования экономят часы. |
| «Протестирую, если возникнут проблемы» | Проблемы = агенты не могут использовать скил. Тестируй ДО развёртывания. |
| «Слишком утомительно тестировать» | Тестировать менее утомительно, чем отлаживать плохой скил в production. |
| «Я уверен, что он хорош» | Самоуверенность гарантирует проблемы. Всё равно протестируй. |
| «Достаточно теоретической проверки» | Прочитать ≠ использовать. Протестируй сценарии применения. |
| «Нет времени на тесты» | Развёртывание непротестированного скила тратит больше времени на последующие исправления. |

**Всё это означает: тестируй перед развёртыванием. Без исключений.**

## Подбирай форму под тип сбоя

Прежде чем писать рекомендации, классифицируй базовый сбой. Форма, которая «бронирует» один тип сбоя, ощутимо вредит при другом.

| Базовый сбой | Правильная форма | Неправильная форма |
|---|---|---|
| Пропускает/нарушает правило под давлением (знает, как правильно, но делает иначе) | Запрет + таблица оправданий + красные флаги (см. references/bulletproofing.md) | Мягкие рекомендации («предпочитай...», «рассмотри...») |
| Следует правилам, но результат имеет неверную форму (раздутый промпт, потерянный вердикт, пересказ спецификации) | Позитивный рецепт или контракт: опиши, чем результат ЯВЛЯЕТСЯ — его части по порядку | Список запретов («не пересказывай», «никогда не комментируй») |
| Пропускает обязательный элемент в том, что уже создаёт | Структурное решение: ОБЯЗАТЕЛЬНОЕ поле или слот в шаблоне, который они заполняют | Напоминания в тексте рядом с шаблоном |
| Поведение должно зависеть от условия | Условие, привязанное к наблюдаемому предикату («если бриф существует, сошлись на него») | Безусловное правило с оговорками-исключениями |

**Почему запреты дают обратный эффект при проблемах формы:** при конкурирующем стимуле («сделай промпт самодостаточным») агенты торгуются с запретом «не делай X». В сравнительных тестах формулировок для рекомендаций по промптам диспетчеризации вариант с запретом давал заметно больше нежелательного содержимого, чем вариант с рецептом (распределения полностью разделились), и показывал тенденцию быть хуже даже контроля без рекомендаций — проводи микротесты на своём случае, а не предполагай, но никогда не берись за запрет по умолчанию. Рецепту не о чем торговаться: результат либо соответствует заданной форме, либо нет.

**Правила для любой выбранной формы:**
- **Никаких оговорок с нюансами.** «Не делай X, если это неважно» заново открывает торг — добавление одной оговорки с нюансом к выигрышному рецепту ухудшало его с стабильного до шумного в тех же тестах формулировок. Настоящее исключение выражай отдельным условием на наблюдаемом предикате.
- **Оговорки-исключения не ограничивают область.** «Это ограничение не относится к блокам кода» всё равно подавляет блоки кода. Если часть результата должна быть исключена, перестрой правило так, чтобы оно не могло её затронуть.

## Защита от рационализации

Когда базовый сбой — это сбой дисциплины, прочитай
[references/bulletproofing.md](references/bulletproofing.md), прежде чем писать
рекомендации: закрытие лазеек, граница между духом и буквой правила,
таблица оправданий и список красных флагов.

## RED-GREEN-REFACTOR для скилов

Следуй циклу TDD:

### RED: напиши падающий тест (базовый прогон)

Запусти сценарий давления с субагентом БЕЗ скила. Задокументируй точное поведение:
- Какие выборы они сделали?
- Какие оправдания они использовали (дословно)?
- Какие давления спровоцировали нарушения?

Это и есть «увидеть падение теста» — ты должен увидеть, что агенты делают по умолчанию, прежде чем писать скил.

### GREEN: напиши минимальный скил

Напиши скил, который закрывает именно эти оправдания. Не добавляй лишнего содержимого для гипотетических случаев.

Запусти те же сценарии С скилом. Теперь агент должен следовать правилам.

### REFACTOR: закрой лазейки

Агент нашёл новое оправдание? Добавь явный контраргумент. Перетестируй, пока не станет неуязвимо.

### Микротестируй формулировки перед полными сценариями

Полные прогоны сценариев давления — это финальный барьер, но они медленные и дорогие для каждой итерации. Сначала проверь саму формулировку микротестами:

1. **Один образец со свежим контекстом на вызов** — сырой вызов API или одноразовый субагент, если у тебя нет доступа к API. Системный промпт = реалистичный контекст, в котором будут жить рекомендации (полный скил или шаблон промпта, а не рекомендации в изоляции); сообщение пользователя = задача, провоцирующая сбой.
2. **Всегда включай контроль без рекомендаций.** Если в контроле сбой не проявляется, чинить нечего — остановись, не пиши рекомендации.
3. **5+ повторов на вариант.** Единичные образцы лгут.
4. **Вручную читай каждое помеченное совпадение.** Можешь оценивать программно, но отголоски шаблона и процитированные контрпримеры маскируются под попадания; одни только автоматические подсчёты завышают и сбой, и успех.
5. **Дисперсия — это метрика.** Когда рекомендации работают, повторы сходятся к одной форме. Пять разных трактовок за пять повторов означают, что формулировка не связывает — ужесточи форму, прежде чем добавлять слова.

Микротесты проверяют формулировки; они не заменяют сценарии давления для скилов дисциплины.

**Методология тестирования:** полную методологию тестирования смотри в [references/testing-skills-with-subagents.md](references/testing-skills-with-subagents.md):
- Как писать сценарии давления
- Типы давления (время, вложенные усилия, авторитет, усталость)
- Систематическое закрытие дыр
- Приёмы метатестирования

## Антипаттерны

### ❌ Повествовательный пример
"In session 2025-10-03, we found empty projectDir caused..."
**Чем плох:** слишком конкретен, не переиспользуется

### ❌ Размывание многоязычностью
example-js.js, example-py.py, example-go.go
**Чем плох:** посредственное качество, бремя поддержки

### ❌ Код в блок-схемах
```dot
step1 [label="import fs"];
step2 [label="read file"];
```
**Чем плох:** нельзя скопировать и вставить, трудно читать

### ❌ Обобщённые метки
helper1, helper2, step3, pattern4
**Чем плох:** метки должны нести смысл

## СТОП: перед переходом к следующему скилу

**После написания ЛЮБОГО скила ты ОБЯЗАН ОСТАНОВИТЬСЯ и пройти процесс развёртывания.**

**НЕ делай:**
- Не создавай несколько скилов пакетом без тестирования каждого
- Не переходи к следующему скилу, пока текущий не проверен
- Не пропускай тестирование на основании «пакетная работа эффективнее»

**Чек-лист развёртывания ниже ОБЯЗАТЕЛЕН для КАЖДОГО скила.**

Развёртывание непротестированных скилов — это развёртывание непротестированного кода. Это нарушение стандартов качества.

## Чек-лист создания скила (адаптация TDD)

**ВАЖНО: создай задачу (todo) для КАЖДОГО пункта чек-листа ниже.**

**Фаза RED — напиши падающий тест:**
- [ ] Создай сценарии давления (3+ совмещённых давления для скилов дисциплины)
- [ ] Запусти сценарии БЕЗ скила — задокументируй базовое поведение дословно
- [ ] Выяви закономерности в оправданиях/сбоях

**Фаза GREEN — напиши минимальный скил:**
- [ ] Имя использует только буквы, цифры, дефисы (без скобок и спецсимволов)
- [ ] YAML frontmatter с обязательными полями `name` и `description` (максимум 1024 символа; см. [спецификацию](https://agentskills.io/specification))
- [ ] Описание начинается с «Use when...» («Используй при...») и содержит конкретные триггеры/симптомы
- [ ] Описание написано в третьем лице
- [ ] Ключевые слова по всему тексту для поиска (ошибки, симптомы, инструменты)
- [ ] Понятный обзор с ключевым принципом
- [ ] Закрыты конкретные базовые сбои, выявленные на фазе RED
- [ ] Форма рекомендаций соответствует типу сбоя (см. «Подбирай форму под тип сбоя»)
- [ ] Для рекомендаций, формирующих поведение: формулировка прошла микротест с контролем без рекомендаций (5+ повторов, каждое помеченное совпадение прочитано вручную) — неприменимо для чисто справочных скилов
- [ ] Код внутри файла ИЛИ ссылка на отдельный файл
- [ ] Один отличный пример (не многоязычный)
- [ ] Запусти сценарии С скилом — убедись, что агенты теперь следуют правилам

**Фаза REFACTOR — закрой лазейки:**
- [ ] Выяви НОВЫЕ оправдания по итогам тестирования
- [ ] Добавь явные контраргументы (если это скил дисциплины)
- [ ] Построй таблицу оправданий из всех итераций тестирования
- [ ] Создай список красных флагов
- [ ] Перетестируй, пока не станет неуязвимо

**Проверки качества:**
- [ ] Небольшая блок-схема — только если решение неочевидно
- [ ] Таблица быстрого справочника
- [ ] Раздел с типичными ошибками
- [ ] Никакого повествования-рассказа
- [ ] Вспомогательные файлы — только для инструментов или объёмных справочников

**Развёртывание:**
- [ ] Закоммить скил в git и отправь в свой форк (если настроен)
- [ ] Подумай о вкладе обратно через PR (если он широко полезен)

## Процесс обнаружения

Как будущие агенты находят твой скил:

1. **Сталкиваются с проблемой** («тесты нестабильны»)
2. **Ищут скилы** (grep по описаниям, просмотр категорий)
3. **Находят SKILL** (описание совпадает)
4. **Просматривают обзор** (это релевантно?)
5. **Читают паттерны** (таблица быстрого справочника)
6. **Загружают пример** (только при реализации)

**Оптимизируй под этот процесс** — размещай искомые термины рано и часто.
