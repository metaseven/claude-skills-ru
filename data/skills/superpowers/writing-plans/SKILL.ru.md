# Написание планов

## Обзор

Пиши планы реализации для инженера, который не видел ни этой кодовой базы, ни этой спецификации. Считай, что он пишет идиоматичный код на языке проекта, как только знает точный интерфейс и точный тест, и что он сделает разумный выбор там, где план оставляет свободу. Чего он знать не может — так это твоих решений: какие файлы, какие имена и сигнатуры, какие значения из спецификации, какие тесты доказывают каждую задачу. Всё это нужно зафиксировать. Давай весь план целиком в виде небольших задач. DRY. YAGNI. TDD. Частые коммиты.

**Объяви в начале:** «Использую скил writing-plans, чтобы составить план реализации.»

**Контекст:** Если работаешь в изолированном worktree, он должен был быть создан через скил `superpowers:using-git-worktrees` на этапе выполнения.

**Сохраняй планы в:** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- (Предпочтения пользователя по месту хранения планов важнее этого значения по умолчанию)

## Проверка области

Если спецификация охватывает несколько независимых подсистем, её следовало разбить на под-спецификации на этапе брейнсторминга. Если этого не сделали, предложи разбить работу на отдельные планы — по одному на подсистему. Каждый план должен давать работающее, тестируемое программное обеспечение само по себе.

## Структура файлов

Прежде чем определять задачи, нанеси на карту, какие файлы будут созданы или изменены и за что отвечает каждый из них. Именно здесь фиксируются решения о декомпозиции.

- Проектируй единицы с понятными границами и чётко определёнными интерфейсами. У каждого файла — одна ясная ответственность.
- Лучше всего ты рассуждаешь о коде, который помещается в контекст целиком, а правки надёжнее, когда файлы сфокусированы. Предпочитай небольшие сфокусированные файлы большим, которые делают слишком много.
- Файлы, которые меняются вместе, должны жить вместе. Разделяй по ответственности, а не по техническому слою.
- В существующих кодовых базах следуй установленным паттернам. Если в проекте принято держать большие файлы, не перестраивай их самовольно. Но если изменяемый файл стал громоздким, включить его разделение в план разумно.

Эта структура задаёт декомпозицию задач. Каждая задача должна давать самодостаточные изменения, которые имеют смысл независимо.

## Размер задач

Задача — наименьшая единица, у которой есть собственный цикл тестирования и которая стоит проверки свежим ревьюером. При определении границ задач: объединяй шаги настройки, конфигурации, каркаса и документации с той задачей, результат которой их требует; разделяй только там, где ревьюер мог бы обоснованно отклонить одну задачу и принять соседнюю. Каждая задача заканчивается независимо проверяемым результатом.

## Гранулярность шагов

**Каждый шаг — одно действие с проверяемым результатом:**
- «Напиши падающий тест» — шаг
- «Запусти его и убедись, что тест падает» — шаг
- «Реализуй минимальный код, чтобы тест прошёл» — шаг
- «Запусти тесты и убедись, что они проходят» — шаг
- «Коммит» — шаг

## Заголовок документа плана

**Каждый план ОБЯЗАТЕЛЬНО начинается с этого заголовка:**

```markdown
# [Feature Name] Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** [One sentence describing what this builds]

**Architecture:** [2-3 sentences about approach]

**Tech Stack:** [Key technologies/libraries]

**Spec:** [path to the spec/design doc this plan implements — the plan
argues from the spec, so the spec travels with it; executors read both]

## Global Constraints

[The spec's project-wide requirements — version floors, dependency limits,
naming and copy rules, platform requirements — one line each, with exact
values copied verbatim from the spec. Every task's requirements implicitly
include this section.]

## Review Focus

[The five input classes or failure modes the spec implies but no task's
tests exercise that are most likely to bite a person using this software
— one line each, naming the input or condition and the behavior a
reasonable person would expect, most likely first. The spec is a vision
document: it says what the software must do, not everything it will
meet, and its silence on an input is not permission for that input to
break the program. Write the list here, once, with the spec in front of
you. Then, for each line, add the test that pins it to the task that
owns the code, in that task's own step style.]

---
```

## Структура задачи

````markdown
### Task N: [Component Name]

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test: `tests/exact/path/to/test.py`

**Interfaces:**
- Consumes: [what this task uses from earlier tasks — exact signatures]
- Produces: [what later tasks rely on — exact function names, parameter
  and return types. A task's implementer sees only their own task; this
  block is how they learn the names and types neighboring tasks use.]

- [ ] **Step 1: Write the failing test**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **Step 2: Run test to verify it fails**

Run: `pytest tests/path/test.py::test_name -v`
Expected: FAIL with "function not defined"

- [ ] **Step 3: Implement `function(input: InputType) -> ResultType` in `exact/path/to/file.py`**

One line on the approach when the signature and the test leave a choice
(which library call, which data structure); a code block only for an
algorithm they do not determine.

- [ ] **Step 4: Run test to verify it passes**

Run: `pytest tests/path/test.py::test_name -v`
Expected: PASS

- [ ] **Step 5: Commit**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## Что содержит шаг

Шаг готов, когда исполнитель может написать из него ровно одно разумное действие. Это и есть всё требование: однозначно, но не исчерпывающе. Каждый вид шага несёт только то, что делает его однозначным, и ничего сверх:

- **Шаг с тестом:** имя теста и его проверки в виде кода, с точными значениями из спецификации.
- **Шаг с кодом:** точная сигнатура (имя, параметры, тип возвращаемого значения), файл, в котором она живёт, и конкретные значения, которые фиксирует спецификация. Тело функции пишет исполнитель. Тело приводится только для алгоритма, который сигнатура и тесты не определяют, или для точного текста, зафиксированного спецификацией.
- **Шаг проверки:** команда для запуска и вывод, по которому понятно, что проверка прошла.
- **Ссылка на другую задачу:** блок Interfaces этой задачи говорит, что использовать; план не повторяет её код.

План — это набор решений, которые исполнитель не может принять сам. План длиннее описываемого кода — значит, он написал код вместо плана. Строки, которые ничего не решают («TBD», «обработать граничные случаи», «добавить подходящую валидацию», «написать тесты для всего выше», тип или функция, которые ни одна задача не определяет), — это противоположная ошибка, и её ловит самопроверка.

## Самопроверка

Когда план написан целиком, перечитай спецификацию свежим взглядом и сверь с ней план. Это список проверок, который ты выполняешь сам, — не запуск субагента.

**1. Покрытие спецификации:** пройдись по каждому разделу и требованию спецификации. Можешь ли ты указать задачу, которая его реализует? Перечисли все пробелы.

**2. Проверка шагов:** каждый шаг должен позволять исполнителю написать ровно одно разумное действие, и ни один шаг не должен нести больше. Строка, которая ничего не решает, — пробел. Тело функции, которое сигнатура и тесты уже определяют, — стенограмма. Исправь оба случая.

**3. Согласованность типов:** совпадают ли типы, сигнатуры методов и имена свойств, которые ты использовал в поздних задачах, с тем, что определено в ранних? Функция `clearLayers()` в задаче 3 и `clearFullLayers()` в задаче 7 — это ошибка.

**4. Фокус ревью:** для каждого класса входных данных или режима отказа, которые подразумевает спецификация, есть ли задача, чьи тесты их проверяют? Пять непокрытых, которые с наибольшей вероятностью подведут человека, попадают в раздел Review Focus, и для каждой строки там добавляется тест в задачу-владелец. Пустой раздел означает, что проверку ты сделал и ничего не нашёл, а не что ты её пропустил.

**5. Пропорции:** сравни длину плана с длиной спецификации. План, в несколько раз длиннее реализуемой спецификации, — это стенограмма программы, а не план. Если блоки кода занимают большую часть документа, замени тела сигнатурами, именами тестов и проверками и убедись, что каждый шаг всё ещё однозначен.

Если находишь проблемы, исправляй их на месте. Перепроверять не нужно — исправь и двигайся дальше. Если найдено требование спецификации без задачи, добавь задачу.

## Передача к выполнению

После сохранения и самопроверки плана дай ссылку на него человеку-партнёру для чтения. Если он уже явно указал способ выполнения, попроси проверить план и подтвердить, что тот отражает желаемое; дождись этой проверки до начала реализации и используй уже выбранный способ. Иначе попроси проверить план и выбрать способ выполнения до начала реализации.

**Когда способ выполнения не указан:**

**«План готов и сохранён в `docs/superpowers/plans/<filename>.md`. Пожалуйста, проверь план. Какой подход к выполнению предпочитаешь?»**

- **Субагенты** — свежий субагент реализует каждую задачу, а свежий ревьюер проверяет её до начала следующей, в конце — ревью всей ветки. Самый тщательный вариант; стоит свежего контекста на каждую задачу и на каждое ревью.
- **Нативно** — все задачи я выполняю сам в этой сессии, так, как работает эта среда, а затем один свежий ревьюер на самой мощной модели проверяет всю ветку. Самый дешёвый и быстрый вариант; независимой проверки до конца не будет. Хорошо работает с моделью среднего уровня, так как план уже содержит проектные решения.

**Для этого плана я рекомендую <один из двух вариантов>, потому что <одно предложение из плана: насколько задачи зависят от интерфейсов друг друга, сколько их и во что обойдётся ошибка, попавшая в релиз>. План отражает то, что ты хочешь, и какой подход используем?»**

**Когда способ выполнения уже указан:**

**«План готов и сохранён в `docs/superpowers/plans/<filename>.md`. Пожалуйста, проверь план. Отражает ли он то, что ты хочешь?»**

**Если выбраны субагенты:**
- **ОБЯЗАТЕЛЬНЫЙ ПОД-СКИЛ:** используй superpowers:subagent-driven-development

**Если выбран нативный режим:**
- **ОБЯЗАТЕЛЬНЫЙ ПОД-СКИЛ:** используй superpowers:executing-plans
