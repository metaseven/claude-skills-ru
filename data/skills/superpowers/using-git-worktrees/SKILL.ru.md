# Использование Git Worktrees

## Обзор

Убедись, что работа ведётся в изолированном рабочем пространстве. Предпочитай нативные инструменты worktree твоей платформы. Вручную создавай git worktree только тогда, когда нативного инструмента нет.

**Основной принцип:** сначала проверь, не изолирован ли ты уже. Затем используй нативные инструменты. Затем откатись к git. Никогда не борись с окружением (harness).

**Сообщи в начале:** «Использую скил using-git-worktrees, чтобы настроить изолированное рабочее пространство.»

## Шаг 0: Проверь существующую изоляцию

**Перед созданием чего-либо проверь, не находишься ли ты уже в изолированном рабочем пространстве.**

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)
```

**Защита от submodule:** `GIT_DIR != GIT_COMMON` также истинно внутри git submodule. Прежде чем считать, что ты находишься в worktree, убедись, что это не submodule:

```bash
# If this returns a path, you're in a submodule, not a worktree — treat as normal repo
git rev-parse --show-superproject-working-tree 2>/dev/null
```

**Если `GIT_DIR != GIT_COMMON` (и это не submodule):** ты уже находишься в связанном worktree. Переходи к шагу 2 (настройка проекта). НЕ создавай ещё один worktree.

Сообщи о состоянии ветки:
- На ветке: «Уже в изолированном рабочем пространстве по пути `<path>` на ветке `<name>`.»
- Detached HEAD: «Уже в изолированном рабочем пространстве по пути `<path>` (detached HEAD, управляется извне). Создание ветки понадобится на этапе завершения.»

**Если `GIT_DIR == GIT_COMMON` (или это submodule):** ты находишься в обычной копии репозитория.

Указывал ли пользователь свои предпочтения по worktree в инструкциях? Если нет, перед созданием worktree запроси согласие:

> «Хочешь, я настрою изолированный worktree? Это защитит твою текущую ветку от изменений.»

Используй уже заявленное предпочтение без повторного вопроса. Если пользователь отказывается, работай на месте и переходи к шагу 2.

## Шаг 1: Создай изолированное рабочее пространство

**У тебя есть два механизма. Пробуй их в таком порядке.**

### 1a. Нативные инструменты worktree (предпочтительно)

Пользователь попросил изолированное рабочее пространство (согласие на шаге 0). Есть ли у тебя способ создать worktree? Это может быть инструмент с именем вроде `EnterWorktree`, `WorktreeCreate`, команда `/worktree` или флаг `--worktree`. Если есть, используй его и переходи к шагу 2.

Нативные инструменты сами управляют размещением каталога, созданием ветки и очисткой. Если использовать `git worktree add`, когда есть нативный инструмент, появится скрытое состояние, которое окружение не видит и не может контролировать.

Переходи к шагу 1b, только если нативного инструмента worktree нет.

### 1b. Откат к git worktree

**Используй это, только если шаг 1a неприменим** — нативного инструмента worktree нет. Создай worktree вручную через git.

#### Выбор каталога

Следуй такому порядку приоритетов. Явное предпочтение пользователя всегда важнее наблюдаемого состояния файловой системы.

1. **Проверь инструкции на наличие заявленного каталога worktree.** Если пользователь уже его указал, используй без вопросов.

2. **Проверь наличие существующего каталога worktree внутри проекта:**
   ```bash
   ls -d .worktrees 2>/dev/null     # Preferred (hidden)
   ls -d worktrees 2>/dev/null      # Alternative
   ```
   Если найден, используй его. Если есть оба, побеждает `.worktrees`.

3. **Если других указаний нет**, по умолчанию используй `.worktrees/` в корне проекта.

#### Проверка безопасности (только для каталогов внутри проекта)

**ОБЯЗАТЕЛЬНО проверь, что каталог игнорируется git, перед созданием worktree:**

```bash
git check-ignore -q .worktrees 2>/dev/null || git check-ignore -q worktrees 2>/dev/null
```

**Если НЕ игнорируется:** добавь его в .gitignore, закоммить изменение и продолжай.

**Почему это критично:** так предотвращается случайный коммит содержимого worktree в репозиторий.

#### Создание worktree

```bash
# Determine path based on chosen location
path="$LOCATION/$BRANCH_NAME"

git worktree add "$path" -b "$BRANCH_NAME"
cd "$path"
```

**Запасной вариант для песочницы:** если `git worktree add` завершается ошибкой доступа (песочница заблокировала действие), сообщи пользователю, что песочница заблокировала создание worktree, и что ты работаешь в текущем каталоге. Затем выполни настройку и проверку базовых тестов на месте.

## Шаг 2: Настройка проекта

Определи тип проекта автоматически и запусти подходящую настройку:

```bash
# Node.js
if [ -f package.json ]; then npm install; fi

# Rust
if [ -f Cargo.toml ]; then cargo build; fi

# Python
if [ -f requirements.txt ]; then pip install -r requirements.txt; fi
if [ -f pyproject.toml ]; then poetry install; fi

# Go
if [ -f go.mod ]; then go mod download; fi
```

## Шаг 3: Проверь чистую базовую точку

Запусти тесты, чтобы убедиться, что рабочее пространство стартует чистым:

```bash
# Use project-appropriate command
npm test / cargo test / pytest / go test ./...
```

**Если тесты падают:** сообщи о сбоях и спроси, продолжать ли или разбираться.

**Если тесты проходят:** сообщи, что всё готово.

## Краткая справка

| Ситуация | Действие |
|-----------|--------|
| Уже в связанном worktree | Пропусти создание (шаг 0) |
| В submodule | Считай обычным репозиторием (защита шага 0) |
| Есть нативный инструмент worktree | Используй его (шаг 1a) |
| Нативного инструмента нет | Откат к git worktree (шаг 1b) |
| Существует `.worktrees/` | Используй его (проверь, что игнорируется) |
| Существует `worktrees/` | Используй его (проверь, что игнорируется) |
| Существуют оба | Используй `.worktrees/` |
| Нет ни одного | Проверь файл инструкций, затем по умолчанию `.worktrees/` |
| Каталог не игнорируется | Добавь в .gitignore + закоммить |
| Ошибка доступа при создании | Запасной вариант песочницы, работай на месте |
| Тесты падают на базовой проверке | Сообщи о сбоях и спроси |
| Нет package.json/Cargo.toml | Пропусти установку зависимостей |

## Типичные отговорки

| Отговорка | Реальность |
|-----------|--------|
| «Я явно не в worktree — проверять не нужно» | Выполни шаг 0. Изоляция, созданная окружением, и submodule одинаково обманывают на глаз; команды проверки дают точный ответ. |
| «`git worktree add` быстрее, чем искать нативный инструмент» | Нативный инструмент (например, `EnterWorktree`) отвечает за размещение, ветки и очистку. Обход его — главная ошибка: возникает скрытое состояние, которое окружение не видит и не может контролировать. |
| «Каталог worktree, наверняка, уже игнорируется» | Выполни `git check-ignore`. Неигнорируемый каталог worktree закоммитит всё дерево в репозиторий. |
| «Любое имя каталога подойдёт» | Явные инструкции важнее существующего каталога внутри проекта, который важнее значения по умолчанию `.worktrees/`. |
| «Рабочее пространство новое — базовые тесты подождут» | Грязная базовая точка делает неоднозначной каждую последующую ошибку. Запусти тесты сейчас; продолжать дальше при сбоях решает твой человек-партнёр. |
