# Систематическая отладка

## Обзор

**Основной принцип:** ВСЕГДА сначала найди первопричину, и только потом пробуй исправления. Исправление симптомов — это провал.

**Нарушить букву этого процесса — значит нарушить и его дух.**

## Железный закон

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

Если ты не завершил Фазу 1, ты не можешь предлагать исправления.

## Когда использовать

Используй для ЛЮБОЙ технической проблемы:
- Падения тестов
- Баги в продакшене
- Неожиданное поведение
- Проблемы с производительностью
- Ошибки сборки
- Проблемы интеграции

**Особенно ВАЖНО использовать, когда:**
- Есть давление по времени (в авариях соблазн угадывать очень велик)
- Кажется, что нужно «всего одно быстрое исправление»
- Ты уже пробовал несколько исправлений
- Предыдущее исправление не сработало
- Ты до конца не понимаешь проблему

**Не пропускай процесс, если:**
- Проблема кажется простой (у простых багов тоже есть первопричины)
- Ты торопишься (спешка гарантирует переделку)
- Руководитель требует починить СЕЙЧАС (систематический подход быстрее, чем метание наугад)

## Четыре фазы

ОБЯЗАТЕЛЬНО завершай каждую фазу, прежде чем переходить к следующей.

### Фаза 1: Поиск первопричины

**ПЕРЕД тем как пробовать ЛЮБОЕ исправление:**

1. **Внимательно читай сообщения об ошибках**
   - Не пропускай ошибки и предупреждения
   - Часто в них уже есть точный ответ
   - Читай стек вызовов целиком
   - Обрати внимание на номера строк, пути к файлам, коды ошибок

2. **Воспроизводи проблему стабильно**
   - Можешь ли ты вызвать её надёжно?
   - Каковы точные шаги?
   - Происходит ли это каждый раз?
   - Если не воспроизводится → собери больше данных, не угадывай

3. **Проверь недавние изменения**
   - Что изменилось, что могло вызвать это?
   - Git diff, недавние коммиты
   - Новые зависимости, изменения конфигурации
   - Различия в окружении

4. **Собирай доказательства в многокомпонентных системах**

   **КОГДА система состоит из нескольких компонентов (CI → сборка → подпись, API → сервис → база данных):**

   **ПЕРЕД тем как предлагать исправления, добавь диагностические инструменты:**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **Пример (многоуровневая система):**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo SET || echo UNSET)"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "IDENTITY in environment" || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **Это показывает:** какой уровень ломается (секреты → workflow ✓, workflow → сборка ✗)

5. **Прослеживай поток данных**

   **КОГДА ошибка глубоко в стеке вызовов:**

   См. `root-cause-tracing.md` в этой папке — там полная техника обратной трассировки.

   **Краткая версия:**
   - Откуда возникает неверное значение?
   - Что вызвало это с неверным значением?
   - Продолжай трассировку вверх, пока не найдёшь источник
   - Исправляй у источника, а не в месте симптома

### Фаза 2: Анализ закономерностей

**Найди закономерность до исправления:**

1. **Найди рабочие примеры**
   - Найди похожий работающий код в той же кодовой базе
   - Что работает похожим образом на то, что сломано?

2. **Сравни с эталонами**
   - Если реализуешь какой-то паттерн, прочитай эталонную реализацию ПОЛНОСТЬЮ
   - Не пробегай глазами — прочитай каждую строку
   - Полностью пойми паттерн, прежде чем применять его

3. **Определи различия**
   - Что отличается между рабочим и сломанным?
   - Перечисли каждое различие, каким бы мелким оно ни было
   - Не предполагай, что «это не может иметь значения»

4. **Пойми зависимости**
   - Какие другие компоненты нужны этому?
   - Какие настройки, конфигурация, окружение?
   - Какие допущения он делает?

### Фаза 3: Гипотеза и проверка

**Научный метод:**

1. **Сформулируй одну гипотезу**
   - Чётко скажи: «Я думаю, что первопричина — X, потому что Y»
   - Запиши её
   - Будь конкретным, а не расплывчатым

2. **Проверяй минимально**
   - Сделай МИНИМАЛЬНО возможное изменение, чтобы проверить гипотезу
   - Одна переменная за раз
   - Не исправляй несколько вещей сразу

3. **Проверь, прежде чем продолжать**
   - Сработало? Да → Фаза 4
   - Не сработало? Сформулируй НОВУЮ гипотезу
   - НЕ добавляй поверх ещё исправления

4. **Когда ты не знаешь**
   - Скажи «Я не понимаю X»
   - Не делай вид, что знаешь
   - Попроси помощи
   - Исследуй глубже

### Фаза 4: Реализация

**Исправляй первопричину, а не симптом:**

1. **Создай падающий тест**
   - Самое простое из возможных воспроизведений
   - Автоматизированный тест, если возможно
   - Одноразовый скрипт проверки, если нет фреймворка
   - ОБЯЗАТЕЛЬНО иметь его ДО исправления
   - Используй скил `superpowers:test-driven-development`, чтобы писать правильные падающие тесты

2. **Внеси одно исправление**
   - Устрани выявленную первопричину
   - ОДНО изменение за раз
   - Никаких «заодно» улучшений
   - Никакого сопутствующего рефакторинга

3. **Проверь исправление**
   - Тест теперь проходит?
   - Не сломались ли другие тесты?
   - Проблема действительно решена?
   - Используй скил `superpowers:verification-before-completion`, прежде чем заявлять об успехе

4. **Если исправление не сработало**
   - ОСТАНОВИСЬ
   - Посчитай: сколько исправлений ты уже пробовал?
   - Если < 3: вернись к Фазе 1 и переанализируй с новой информацией
   - **Если ≥ 3: СТОП, и поставь под вопрос архитектуру (шаг 5 ниже)**
   - НЕ пробуй исправление №4 без обсуждения архитектуры

5. **Если 3+ исправления не сработали: поставь под вопрос архитектуру**

   **Признаки архитектурной проблемы:**
   - Каждое исправление выявляет новое общее состояние, связь или проблему в другом месте
   - Для внедрения исправлений требуется «массивный рефакторинг»
   - Каждое исправление порождает новые симптомы в других местах

   **СТОП, и пересмотри основы:**
   - Фундаментально ли верен этот паттерн?
   - Не продолжаем ли мы держаться за него «по инерции»?
   - Стоит ли перепроектировать архитектуру вместо дальнейшего устранения симптомов?

   **Обсуди с напарником, прежде чем пробовать ещё исправления**

   Это НЕ провалившаяся гипотеза — это неверная архитектура.

## Красные флаги — СТОП и следуй процессу

Если ты поймал себя на таких мыслях:
- «Быстрое решение сейчас, разберусь потом»
- «Просто попробую поменять X и посмотрю, поможет ли»
- «Добавлю несколько изменений и запущу тесты»
- «Пропущу тест, сам проверю вручную»
- «Наверное, это X, сейчас исправлю»
- «Не до конца понимаю, но это может сработать»
- «Паттерн говорит X, но я адаптирую его по-другому»
- «Вот основные проблемы: [список исправлений без исследования]»
- Предлагаешь решения до того, как проследил поток данных
- **«Ещё одна попытка исправления» (когда уже пробовал 2+)**
- **Каждое исправление выявляет новую проблему в другом месте**

**ВСЕ эти признаки означают: СТОП. Вернись к Фазе 1.**

**Если провалилось 3+ исправлений:** поставь под вопрос архитектуру (см. Фазу 4.5)

## Сигналы, что ты делаешь это неправильно

**Обрати внимание на такие замечания напарника:**
- «Разве это не происходит?» — ты предположил, не проверив
- «Это нам покажет...?» — нужно было сначала собрать доказательства
- «Перестань угадывать» — ты предлагаешь исправления, не поняв проблему
- «Подумай как следует» — пересмотри основы, а не только симптомы
- «Мы застряли?» (с раздражением) — твой подход не работает

**Когда видишь такое:** СТОП. Вернись к Фазе 1.

## Типичные отговорки

| Отговорка | Реальность |
|-----------|------------|
| «Проблема простая, процесс не нужен» | У простых проблем тоже есть первопричины. Для простых багов процесс быстрый. |
| «Авария, нет времени на процесс» | Систематическая отладка БЫСТРЕЕ, чем метание наугад. |
| «Сначала попробую это, потом разберусь» | Первое исправление задаёт направление. Делай правильно с самого начала. |
| «Напишу тест после того, как убежусь, что исправление работает» | Непроверенные исправления не держатся. Тест сначала доказывает правоту. |
| «Несколько исправлений сразу экономят время» | Невозможно понять, что сработало. Появляются новые баги. |
| «Референс слишком длинный, адаптирую паттерн» | Частичное понимание гарантирует баги. Читай полностью. |
| «Вижу проблему, сейчас исправлю» | Видеть симптомы ≠ понимать первопричину. |
| «Ещё одна попытка исправления» (после 2+ провалов) | 3+ провала = архитектурная проблема. Пересмотри паттерн, а не исправляй снова. |

## Краткая справка

| Фаза | Ключевые действия | Критерий успеха |
|------|-------------------|-----------------|
| **1. Первопричина** | Читать ошибки, воспроизвести, проверить изменения, собрать доказательства | Понятно ЧТО и ПОЧЕМУ |
| **2. Закономерность** | Найти рабочие примеры, сравнить | Выявлены различия |
| **3. Гипотеза** | Сформулировать теорию, проверить минимально | Подтверждена или новая гипотеза |
| **4. Реализация** | Создать тест, исправить, проверить | Баг устранён, тесты проходят |

## Когда процесс показывает «первопричины нет»

Если систематическое исследование показало, что проблема действительно связана с окружением, зависит от времени или внешняя:

1. Ты завершил процесс
2. Задокументируй, что ты исследовал
3. Реализуй подходящую обработку (повтор, таймаут, сообщение об ошибке)
4. Добавь мониторинг/логирование для будущего исследования

**Но:** 95% случаев «первопричины нет» — это неполное исследование.
