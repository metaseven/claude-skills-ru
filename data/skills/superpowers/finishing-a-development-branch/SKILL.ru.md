# Завершение ветки разработки

## Обзор

**Основной принцип:** Проверь тесты → Определи окружение → Предложи варианты → Выполни выбор → Наведи порядок.

**Объяви в начале:** "Использую скил finishing-a-development-branch, чтобы завершить эту работу."

## Шаг 1: Проверь тесты

Запусти полный набор тестов проекта (`npm test` / `cargo test` / `pytest` / `go test ./...`).

**Если тесты падают**, выведи список падений и остановись — меню появляется только после зелёного прогона:

```
Tests failing (<N> failures). Must fix before completing:

[Show failures]
```

**Если тесты проходят:** переходи к шагу 2.

## Шаг 2: Определи окружение

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# Capture now, while still inside the workspace — Step 5 changes directory
# before cleanup (Step 6) needs this value
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

От этого зависит, какое меню показать и как работает очистка:

| Состояние | Меню | Очистка |
|-----------|------|---------|
| `GIT_DIR == GIT_COMMON` (обычный репозиторий) | Стандартные 3 варианта | Рабочее дерево для очистки отсутствует |
| `GIT_DIR != GIT_COMMON`, именованная ветка | Стандартные 3 варианта | По происхождению (см. шаг 6) |
| `GIT_DIR != GIT_COMMON`, detached HEAD | Урезанные 2 варианта (без слияния) | Управляется внешне — оставить на месте |

## Шаг 3: Определи базовую ветку

Базовая ветка — это та, от которой отделилась текущая работа. Обычно она указана в плане, в переписке или в upstream ветки. Если она не известна, спроси: "Эта ветка отделилась от <твоё лучшее предположение> — так и есть?"
Подтверди перед слиянием: слияние в неправильную базу дорого откатывать.

## Шаг 4: Предложи варианты

**Обычный репозиторий и worktree с именованной веткой — предложи ровно эти 3 варианта:**

```
Implementation complete. What would you like to do?

1. Merge back to <base-branch> locally
2. Push and create a Pull Request
3. Keep the branch as-is (I'll handle it later)

Which option?
```

**Detached HEAD — предложи ровно эти 2 варианта:**

```
Implementation complete. You're on a detached HEAD (externally managed workspace).

1. Push as new branch and create a Pull Request
2. Keep as-is (I'll handle it later)

Which option?
```

Выводи меню ровно в таком виде — кратко, с каждым вариантом из списка выше. Удаление работы происходит только по прямой просьбе твоего партнёра (см. раздел "Если партнёр просит отбросить работу" ниже). Дождись ответа: решение об интеграции принимает он.

## Шаг 5: Выполни выбор

### Вариант 1: Слияние локально

```bash
# Get main repo root for CWD safety
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# Merge first — verify success before removing anything
git checkout <base-branch>
git pull
git merge <feature-branch>

# Verify tests on merged result
<test command>
```

Если тесты падают на результате слияния: остановись, оставь worktree и ветку на месте и разберись в причине. Ничего не отправлено, поэтому слияние локальное и его можно восстановить.

Когда результат слияния зелёный: очисти worktree (шаг 6), затем удали ветку:

```bash
git branch -d <feature-branch>
```

### Вариант 2: Отправить и создать PR

```bash
git push -u origin <feature-branch>
# From a detached HEAD, name the new branch on the remote:
# git push origin HEAD:refs/heads/<new-branch>
```

Затем создай pull/merge request в <base-branch> средствами хостинга — его CLI, если он доступен, или ссылкой на создание, которую большинство хостингов выводят при пуше. Следуй шаблону и соглашениям репозитория, если они есть, и сообщи партнёру URL.

Worktree сохрани — партнёр дорабатывает работу там по замечаниям к PR.

### Вариант 3: Оставить как есть

Сообщи: "Ветка <name> сохранена. Worktree оставлен в <path>."

### Если партнёр просит отбросить работу

Этот путь существует только как ответ на явную просьбу выбросить работу. Сначала подтверди:

```
This will permanently delete:
- Branch <name>
- All commits: <commit-list>
- Worktree at <path>

Type 'discard' to confirm.
```

Дождись именно этого подтверждения. Когда оно пришло:

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

Затем очисти worktree (шаг 6) и принудительно удали ветку:

```bash
git branch -D <feature-branch>
```

## Шаг 6: Очистка рабочей области

**Выполняется для варианта 1 и подтверждённого удаления.** Варианты 2 и 3 всегда сохраняют worktree. Оба сценария уже перешли в корень основного репозитория — удаление worktree должно выполняться снаружи него — и используют значения `GIT_DIR`/`GIT_COMMON`/`WORKTREE_PATH`, сохранённые на шаге 2, до смены каталога.

**Если `GIT_DIR == GIT_COMMON`:** обычный репозиторий, worktree для очистки нет. Готово.

**Если `WORKTREE_PATH` находится в `.worktrees/` или `worktrees/`:** worktree создан Superpowers — очистку ведём мы:

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune  # Self-healing: clean up any stale registrations
```

**Если удаление отклонено** (`contains modified or untracked files`): в worktree есть файлы, которых нигде больше нет — незакоммиченные планы, заметки или черновики. Никогда не используй `--force` по собственной инициативе. Покажи партнёру, что под угрозой, и спроси:

```bash
git -C "$WORKTREE_PATH" status --porcelain -uall
```

```
Worktree removal refused — these files were never committed:

<file list>

1. Commit them to <branch> before cleanup
2. Move them into <main repo root>
3. Delete them (unrecoverable)

Which?
```

Выполни выбор, затем удали worktree.

**Иначе:** рабочая область принадлежит хост-окружению — оставь её на месте. Если платформа предоставляет инструмент выхода из рабочей области, используй его.

## Краткая справка

| Вариант | Слияние | Пуш | Сохранить worktree | Удалить ветку |
|---------|---------|-----|--------------------|---------------|
| 1. Слить локально | да | - | - | да |
| 2. Создать PR | - | да | да | - |
| 3. Оставить как есть | - | - | да | - |
| Отбросить (только по явной просьбе) | - | - | - | да (принудительно) |

## Типичные отговорки

| Отговорка | Реальность |
|-----------|------------|
| "Тесты проходили ранее в этой сессии" | Запусти набор на дереве, которое собираешься интегрировать. Зелёный прогон доказывает только то дерево, на котором он запускался. |
| "Они явно хотят слить" | Интеграция — решение твоего партнёра. Покажи меню и жди. |
| "Похоже, фича готова — предложу отбросить" | Меню полное, как написано. Отбрасывание только тогда, когда партнёр прямо об этом попросит. |
| "'Да, избавься от неё' — это подтверждение" | Удаление разрешает только введённое слово `discard`. |
| "PR уже создан, значит worktree теперь мусор" | Замечания к PR исправляются в этом worktree. Он остаётся, пока работа не влита. |
| "Этот другой worktree выглядит устаревшим — почищу и его" | Чисти только worktree в `.worktrees/` или `worktrees/`. Всё остальное принадлежит хосту. |
| "Удаление отклонено — `--force` просто доделает очистку" | Отказ означает, что файлы существуют только в этом worktree. `--force` уничтожит их безвозвратно. Покажи партнёру и спроси. |
| "Ошибка на результате слияния, наверное, флаки" | Падение результата слияния останавливает всё. Ветка и worktree остаются на месте, пока ты разбираешься. |
| "Базовая ветка очевидно main" | Уточни точку ответвления или спроси. Слияние в неправильную базу дорого откатывать. |
| "Push отклонён — force-push починит" | Отклонённый push значит, что удалённая ветка изменилась. Разберись; делай force-push только по явной просьбе партнёра. |
